## Authoring conventions for the 40 new questions

### Per-tier ML-flavor targets

The v3.9 handoff established that ML-flavor ratio per tier matters for cross-track consistency. Apply these targets to Rust:

| Tier | Target (Pure Rust / ML-adjacent / Explicit ML) | Rationale |
|------|------------------------------------------------|-----------|
| Introductory | 100 / 0 / 0 | Pure language fundamentals only |
| Amateur | 60 / 20 / 20 | Light ML framing where it fits naturally |
| Intermediate | 30 / 30 / 40 | ML-adjacent framing dominant, primitives appear |
| Experienced | 20 / 20 / 60 | Explicit ML primitives expected |
| Master | 10 / 10 / 80 | Capstone-level ML implementations |

Track the actual ratio per tier in your handoff notes. If a tier diverges materially from target, flag it with reasoning.

### Tier progression themes

Per `PROMPTS.md`'s v4.0 prompt:

- **Introductory:** `let`/`let mut`, type suffixes, basic fn, primitives — 5 already shipped in Stage 2 (boolean binding, mut integer, type annotation + f64, println!, immutable Vec). Add 5 more covering: string binding (`&str` vs `String`), `if/else`, function with parameter and return, `match` on a literal, tuple binding.

- **Amateur:** Vec/String/Option/Result, `if let`, `match` on Option. Light ML framing welcome on 2 of 10 (e.g., a question framed around classifying scores into above/below threshold via Option<f64>).

- **Intermediate:** ownership + borrowing, iterators, closures. ML-adjacent framing on 3-4 of 10. Closure-deref variants (`|&w|` vs `|w| *w`) MUST appear in at least one question to exercise `CLOSURE_DEREF_VARIANTS`.

- **Experienced:** traits, generics, lifetimes (IN CONTEXT — no abstract puzzles). 5 already shipped in Stage 2 (trait def, impl, generic identity, struct with lifetime, multi-T fn). Add 5 more covering: trait with default method, generic with multiple trait bounds, struct method with `&mut self`, `impl Iterator for`, `Result<T, E>` returning with `?` operator. Lifetime questions must anchor to a real scenario (struct holding a reference, fn returning a reference) — never abstract.

- **Master:** async/`.await`, unsafe, FFI basics, Rc/Arc/Box. Capstone-level work. The final question (`rs_mas_10`) should be a real ML primitive composition — a forward-pass over a tiny feedforward layer, embedding lookup with cosine similarity, or similar. Not a syntax drill. This is the question users will remember.

### Authoring discipline (load-bearing — re-read before authoring each question)

These are the principles from Stage 1 that produced the Stage 2 calibration miss in the first 10 questions. They must be honored across the next 40:

1. **`structure` must match the prompt, never be tighter.** If the prompt says "filter weights above 0.5" without mandating `.collect()`, the canonical structure doesn't require `.collect()`. Tighter structures reject correct answers and erode user trust.

2. **Each question MUST have a `hint` field.** Hints explain the concept without giving syntax away. Short (1-2 sentences). The Python-vs-Rust gotchas should be flagged where they matter (e.g., lowercase booleans, explicit mutability, `&str` vs `String`).

3. **Use the alternatives library where it earns its keep.** `CLOSURE_DEREF_VARIANTS`, `NUMERIC_LITERAL_SUFFIXES`, `STRING_TYPE_VARIANTS`, `ITER_COLLECT_VARIANTS`, `RESULT_PROPAGATION` exist to keep authoring DRY. If a question's structure has any of these variations, splice the library group: `alternatives: { ...['CLOSURE_DEREF_VARIANTS'] }`.

4. **Lifetime names: `'a` only.** No alternatives for lifetime names. Rust convention is strong; teaching it via the grader is part of the value.

5. **Each question has a `qa` block with 3-5 accept and 3 reject formulations.** The harness validates against these. `expect_msg` strings must match what the grader actually produces (run the harness after authoring each question to verify).

6. **Tags drawn from the closed set only.** `RUST_QUESTION_TAGS` in `build.py` enforces this. Add a new tag to the constant first if a new concept demands one.

7. **Domain framing for thematic continuity.** Where natural, prefer `open_jobs`/`tax_rate`/`invoice` over abstract `x`/`y`/`foo`. Mirrors the SQL and JS tracks' garage-shop framing. Don't force it where it doesn't fit (ML primitives in Master tier are framed around tensors and activations, not auto shops).

### Question authoring workflow

For each question:

1. Draft the assertion (required / forbidden / structure / alternatives) + tags + hint
2. Write 3-5 accept variants exercising whitespace tolerance and alternatives substitution
3. Write 3 reject variants targeting common-mistake patterns the grammar-lite rules can catch
4. Run `python3 tests/qa_harness.py` and confirm green before moving to next question
5. If any qa case fails, fix the question (not the grader). The grader is locked from Stage 2.

Don't sprint 10 questions without running the harness in between. Author 2-3, run harness, fix any issues, author next 2-3. Tight loop catches calibration drift early.

## Content file conventions

### Cheatsheet structure

Follow `src/content/javascript/cheatsheet.md` and `src/content/python/cheatsheet.md` as templates. Whole-language reference, not per-tier. Section headers organize by language area (Variables, Functions, Ownership, Collections, Iterators, Traits, Error Handling, etc.). Tag syntax is `<<tag>>...<</tag>>` (v3.10 migrated; legacy `[tag]` is build-rejected).

### Per-tier file structure

Each `tier-*.md` has:
- A concepts section (top) explaining the tier's core ideas in prose
- A `---` divider
- An examples section with `# EXAMPLE N` headings — 3-5 worked examples per tier

The last example in each tier previews a concept from the next tier (the "bridge" convention from PROMPTS.md).

Examples must never duplicate the graded questions. A user who reads an example and pastes its exact code into a question prompt should NOT pass — the example should teach an adjacent skill that prepares them for the question, not solve the question for them.

### ASCII diagrams where they earn their place

Rust's ownership model is genuinely visual and benefits from ASCII diagrams in the cheatsheet and Intermediate-tier file. Don't draw ASCII for everything; reserve it for concepts where prose alone doesn't land (ownership transfers, lifetime relationships, mutex/refcell distinction).

## What to do if you get stuck

If during authoring you discover a flaw in the locked Stage 1 design — a category of correct Rust answers the grader can't accept, a class of incorrect answers it can't reject, or an alternatives mechanic that doesn't compose with a real question — STOP and surface to the user.

Don't paper over design flaws with ad-hoc rules. Don't add new fields to the assertion type without user approval. Don't change `RustEngine`'s grading logic mid-Stage 3 — that would invalidate every prior question's qa block. If the design needs revision, that's a conversation in main chat (not in this Claude Code session), and Stage 3 pauses until revisions are agreed.

If a tier feels like it's drifting from its ML-flavor target, surface it. The user calibrated these targets deliberately; an off-target tier needs explicit acknowledgment, not silent correction.

If you find yourself authoring questions faster than you can run the harness — slow down. The harness is the regression guard. A failing harness mid-Stage 3 should produce 1-2 broken questions to fix, not 15.
