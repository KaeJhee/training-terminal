## Locked design (from Stage 1)

### Pattern assertion schema

```javascript
{ type: 'pattern',
  required:    [ <substring>, ... ],          // must all appear (mandatory)
  forbidden:   [ <substring>, ... ],          // none may appear (optional)
  structure:   '<canonical answer>',          // ws-normalized compare (optional)
  alternatives:{ <token>: [<equiv>, ...] }    // token equivalences (optional)
}
```

### Grading algorithm (three checks, in order)

1. **Forbidden check.** Any forbidden substring present in normalized user input → fail immediately with a forbidden-specific message ("uses `.clone()` — this question tests filtering without copying").
2. **Required check.** Any required substring missing from normalized user input → fail with a "missing X" message (grammar-lite refines this).
3. **Structure check.** Apply `alternatives` substitution to user input, then exact-compare against `structure`. Mismatch → fail with a structural message (grammar-lite refines this).

Grammar-lite refines failure messages but never decides pass/fail. The three checks are the source of truth for correctness.

### Whitespace normalization

- Collapse all whitespace runs to a single space, then trim.
- Outside string literals (`"..."`, `'...'`, `r"..."`, `r#"..."#`), drop spaces unless both adjacent characters are word-ish (`[A-Za-z0-9_']`).
- This makes `n: i32` ≡ `n:i32` ≡ `Vec<f64>` ≡ `} else {` while keeping `let x` distinct from `letx`.
- String literals preserve their internal whitespace untouched.
- Case-sensitive always (Rust is case-sensitive; `Vec` ≠ `vec`).

### Alternatives mechanics

- Whole-token substitution (word-boundary-respecting), single-pass, longest-match-first per position. Not recursive.
- Apostrophe `'` is part of lifetime tokens (`'a`, `'static`) — treat it as part of the token, not a boundary.
- Substitution applies to user input only, never to `required` or `forbidden` substrings (those stay literal).
- Normalize the alternatives table through the same whitespace rule at expansion time. Without this, `'n:i32'` matches normalized user input but substitutes back the canonical `'n: i32'` (with space), producing a phantom mismatch.
- Also normalize `required` and `forbidden` substrings before the contains-check (so author can write either spacing).

### Alternatives library (five named groups)

Defined as a constant in `RustEngine`. Authors reference by name via the `...['NAME']` syntax in a question's `alternatives` map.

```javascript
const RUST_ALTERNATIVES_LIBRARY = {
  CLOSURE_DEREF_VARIANTS: {
    '|&w| w': ['|w| *w', '|&&w| w']
  },
  NUMERIC_LITERAL_SUFFIXES: {
    '0': ['0i32', '0_i32'],
    '0.0': ['0.0f64', '0_f64']
  },
  STRING_TYPE_VARIANTS: {
    'String': ['&str', '&String']    // for questions where any owned-or-borrowed string form is fine
  },
  ITER_COLLECT_VARIANTS: {
    '.collect()': ['.collect::<Vec<_>>()', '.collect::<Vec<f64>>()', '.collect::<Vec<i32>>()']
  },
  RESULT_PROPAGATION: {
    '?': ['.unwrap()', '.expect("error")']    // early-tier only; later tiers require ? specifically
  }
};
```

### Grammar-lite rules

Triggered only when a check fails. Three branches:

1. **Forbidden branch** — report which specific forbidden substring hit, with the question's `forbid_reason` field if present, else a default message.
2. **Required-missing branch** — report which specific required substring is absent. ("missing `mut`", "missing `;`", "missing `&`")
3. **Structure-mismatch branch** — run a small set of pattern rules against the user input:
   - User has `let` but not `mut` where canonical has `mut` AND question is tagged `mutability` → "binding needs `mut`"
   - User input doesn't end with `;` where canonical does → "missing `;` at end of statement"
   - `&` count mismatch (user has `|w|` where structure expects `|&w|`) → "wrong borrow syntax — try `|&w|` or `*w`"
   - `impl` block missing `for <Type>` → "missing `for <Type>` in impl block"
   - Trailing-comma before `}` mismatch → accept (trailing commas in struct literals are valid Rust; the normalizer should drop these symmetrically)
   - Fallback: character-aligned diff of first 80 chars of user vs canonical.

Question-level `tags` (the closed set below) drive which structure-mismatch rules apply. A borrowing-tagged question shouldn't get a spurious "needs `mut`" hint.

### Closed tag set

Validated at lint time by `build.py --check`:

```python
RUST_QUESTION_TAGS = frozenset({
    'mutability',     # let mut, &mut, mutable references
    'borrowing',      # & references, borrow checker concepts
    'lifetimes',      # 'a annotations, lifetime elision
    'traits',         # trait definitions, impl blocks, trait bounds
    'closures',       # |x| ... syntax, FnOnce/Fn/FnMut
    'iterators',      # iter(), map, filter, collect chains
    'error-handling', # Result, Option, ?, unwrap, panic
    'generics',       # <T>, where clauses
    'macros',         # println!, vec!, custom macro_rules!
    'unsafe',         # unsafe blocks, raw pointers
    'async',          # async fn, .await, futures (Master tier)
})
```

Authors can use multiple tags per question. New tags require adding to the constant first.

### QA harness format

Each question has a `qa` field alongside the assertion:

```javascript
qa: {
  accept: [
    'let mut count = 0;',
    'let mut count = 0i32;',
    'let mut count: i32 = 0;'
  ],
  reject: [
    { input: 'let count = 0;',     expect_msg: 'missing `mut`' },
    { input: 'let mut count = 0',  expect_msg: 'missing `;`' },
    { input: 'mut count = 0;',     expect_msg: 'missing `let`' }
  ]
}
```

The harness:
- For each `accept`: assert grader returns `ok: true`. Failure = pattern is too strict.
- For each `reject`: assert grader returns `ok: false` AND the failure detail contains `expect_msg`. Failure = pattern is too loose OR grammar-lite isn't firing the right rule.
- Output per tier: green/red counts, plus full detail of any failure.

The harness is a Python script that parses the questions out of `src/index.template.html` and runs them against a Python port of the grading logic. Pure dev-time check, not run in the browser. Failures block ship.

### Authoring conventions

These apply to the 10 representative questions in Stage 2:

- **Track key:** `'rust'` (full word). Question ID prefix: `rs_` (matches `py_`/`sql_`/`js_`).
- **Engine class:** `RustEngine`.
- **`structure` matches the prompt, never tighter.** If the prompt doesn't lock something down, the canonical answer doesn't either. This is the discipline that prevents "I got the right answer but the grader said wrong" user-trust failures.
- **Lifetime names: `'a` only.** No alternatives for lifetime names. The Rust community convention is strong enough that accepting `'doc`/`'lt` would teach the wrong lesson. Opinionated over flexible by deliberate design choice.
- **Lifetimes always shown in context.** Anchored to a real scenario (struct holding a reference, fn returning a reference). No abstract lifetime puzzles.
- **ML-adjacent framing welcome but never required.** No question should fail because the user doesn't know ML terms.
