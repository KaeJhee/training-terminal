Working doc, NOT final CHANGELOG prose. At ship time this gets consolidated
into the v4.0 CHANGELOG's `Documented` section (mirroring v3.9's
"approx-tolerance defaults" / "authoring principle for assertion tightness"

Each tier appends findings as authoring proceeds. Captures discipline rules
that emerged during authoring but didn't exist as written rules at the
start of Stage 3.

## Introductory tier

### expect_msg ordering matches the earliest-failing check

The grader runs checks in fixed order: `forbidden` → `required` → structure
match (with alternatives) → grammar-lite refinement. A reject test case's
`expect_msg` must match whichever check fails first for that input.

- Surfaced by **rs_intro_10**'s `[3, 5]` reject. First draft expected
  `"structure mismatch"`, but the `required` entry `(3, 5)` is not a
  substring of `[3, 5]`, so the grader emits `missing `(3, 5)`` at the
  required step — structure match never runs. Fix: update the expect_msg
  to match the actual earliest failure, not the failure the author
  *imagined* would fire.

- Rule: when drafting a reject, mentally walk the grader's check order and
  identify the first check that fails. The expect_msg must be a substring
  of what THAT check emits.

## Amateur tier

### Deliberate-strictness-by-tier judgment calls

Some structurally-correct Rust answers are rejected not because the
grader can't accept them, but because the *tier* is the right place to
teach a specific distinction the loose form would dodge.

- **rs_ama_02** rejects `let greeting = "Hello".to_string();` (no
  annotation) even though it produces a correct owned String. Reason:
  Amateur is the right tier to teach the `&str`-vs-`String` type
  distinction explicitly. The annotation requirement is a *teaching*
  choice anchored to the tier, not a grader limitation.

- Rule: when an answer is technically correct but skips the lesson the
  question exists to teach, rejecting it is defensible — and worth
  flagging in the commit message as a deliberate strictness call rather
  than letting it look like grader fragility.

### Required-vs-alternatives boundary (broadly applicable)

The grader runs `required` substring checks BEFORE applying
`alternatives` substitution. When a question accepts parametric variants
of a token, the `required` entry must be the *invariant prefix*;
alternatives handle the parametrization. Otherwise the alternative is
dead code — the user fails at required-check before alternatives ever
fire.

Applied three times in Amateur:

| Question | required (invariant prefix) | alternatives (parametrization) |
|---|---|---|
| rs_ama_06 | `Some` | `Some(_)` ↔ `Some(x)`/`Some(value)`/`Some(_v)` |
| rs_ama_08 | `prediction.unwrap_or` | `0.0` ↔ `0.0f64`/`0.0_f64` (via `NUMERIC_LITERAL_SUFFIXES`) |
| rs_ama_10 | `Some` | same as rs_ama_06 |

- Rule (for all future Rust questions): when a token has accepted
  variants, put the *invariant prefix* in `required` and let
  `alternatives` handle the parametrization. Same boundary applies to
  any parametric form — closure-deref shapes, numeric literal suffixes,
  string-construction variants, turbofish vs. annotation forms.

### Prompt-specificity over output-correctness

When a prompt names a specific method or syntax, accepting any
semantically-equivalent alternative dilutes the teaching value. The
rejected form is correct Rust but doesn't *teach* what the prompt is
testing.

- **rs_ama_09** rejects `let first_logit = logits.get(0);` even though
  `.get(0)` returns the same `Option<&T>` shape as `.first()` and is
  semantically equivalent here. The prompt names `.first()`
  specifically. Teaching the idiomatic method for "first element of a
  collection" matters more than accepting any form that produces the
  same output.

- Rule: prompt-named methods/syntax should be required. If the
  alternative form is also worth teaching, write a separate question
  for it (don't fold it into this one's alternatives).

### Library reuse confirmation

Stage 2 introduced `RUST_ALTERNATIVES_LIBRARY` with five named groups
(`CLOSURE_DEREF_VARIANTS`, `NUMERIC_LITERAL_SUFFIXES`,
`STRING_TYPE_VARIANTS`, `ITER_COLLECT_VARIANTS`, `RESULT_PROPAGATION`)
designed for cross-tier reuse.

- **rs_ama_08** is the first Amateur-tier reuse of
  `NUMERIC_LITERAL_SUFFIXES` (Stage 2 used it on rs_intro_02 /
  rs_intro_03). The named-groups design composes across tiers as
  intended — the same group handles `let mut counter = 0i32;` at Intro
  and `unwrap_or(0.0f64)` at Amateur with no per-call-site duplication.

- Rule: prefer library-group reuse for any token shape covered by the
  Stage 1 design. Local per-question alternatives are correct when the
  shape isn't in the library (different variable names, different body
  shapes, non-standard variants).

## Intermediate tier

### Comma-separated closure parameter lists normalize cleanly

Multi-argument closures like `|acc, &x| acc + x` (used in
`Iterator::fold`) pass through the normalizer without corruption of the
parameter-list shape:

- `|acc, &x| acc + x` → `|acc,&x|acc+x` (space after `,` dropped because
  next char `&` is non-word; space after `|` dropped because next char
  `a` is a word char but prev `|` is non-word — kept only when BOTH
  sides are word).
- Alt `|acc, x| acc + *x` → `|acc,x|acc+*x`
- Alt `|acc, &&x| acc + x` → `|acc,&&x|acc+x`

The reverse-alt map matches each variant's normalized form to the
canonical normalized form and substitutes in place. The word-boundary
check at the leading `|` works because `|` is non-word, so the matcher
doesn't require an off-token boundary on the left side of the match.

- Implication: per-question alternatives for multi-arg closure-deref
  shapes work mechanically the same as single-arg shapes. The
  `CLOSURE_DEREF_VARIANTS` library group is single-arg by design; multi-arg
  needs per-question alts (rs_int_07's fold is the first such case).

- v4.1 candidate: consider extending `RUST_ALTERNATIVES_LIBRARY` with a
  `FOLD_ACCUMULATOR_DEREF` or similar group if the multi-arg pattern
  repeats more than twice across C++/CUDA tracks.

### `move` requires a non-Copy capture to teach the lesson

Closures with `move` only produce *observable* ownership transfer when
the captured value is non-Copy. `f64`, `i32`, `bool` and other `Copy`
types are duplicated by-value at capture regardless of `move`, so a
question like "capture a `baseline: f64` with `move`" tests syntax but
not semantics — the same closure body with or without `move` produces
identical observable behavior.

- Surfaced during rs_int_08 drafting. Initial draft captured a
  baseline `f64`; switched to `Vec<f64>` (non-Copy) so the `move`
  keyword actually transfers ownership. The hint explicitly distinguishes
  Copy vs non-Copy capture so the student understands *why* `move`
  matters for some types and not others.

- Rule: when a question's lesson is the `move` keyword (or any ownership
  transfer mechanic), the captured value must be a non-Copy type
  (`Vec<T>`, `String`, `Box<T>`, custom structs without `#[derive(Copy)]`,
  etc.). Otherwise the test passes but teaches nothing.

### Architecture validation: rs_int_05 exercises grammar-lite borrow-syntax message end-to-end

The Stage 1 design promised that pattern-match failures on closure-deref
inputs would surface as targeted feedback via grammar-lite's tag-driven
rules (specifically: tag `closures` / `iterators` / `borrowing` plus
canonical containing `|&` plus user input lacking `|&` → emit
`wrong borrow syntax — try \`|&w|\` or \`*w\``). rs_int_05's third
reject case `weights.iter().filter(|w| w > 0.0).count()` is the first
question to trigger this code path under real input.

- Verified end-to-end: the reject does produce the targeted
  `wrong borrow syntax` message, not the fallback `structure mismatch`.
- This is the payoff moment for the whole pattern-match-plus-grammar-lite
  architecture: targeted feedback on a class of mistake the grader can't
  *execute* but can *recognize* via tag-driven structural rules.

### Required can't capture the closure-param invariant when multiple param-pattern forms are accepted (rs_int_04 calibration miss)

The required-vs-alternatives boundary rule from Amateur tier extends to
closure parameter shapes too. rs_int_04's first draft had `|x|` in
`required`, intending to mandate the parameter name `x`. But the
accepted alts `|&x| x * 2` (pattern-deref) and `|x| *x * 2` (body-deref)
have different param-pattern surface: `|&x|` doesn't contain `|x|` as
a substring.

- The invariant across the three accepted forms isn't `|x|` (the
  bare-pattern shape); it's "parameter named `x`" — which can't be
  cleanly captured as a substring without awkward forms like `x|`
  that produce muddled user-facing messages.
- Fix: drop the closure-param entry from `required` entirely. The
  body operation (`* 2`) stays as the meaningful invariant. The
  variable-name case (`|n| n * 2`) falls to structure mismatch with
  the diff, which is informative enough.

- Rule (extends Amateur's boundary rule to closure params): when a
  question accepts multiple closure parameter patterns, do NOT
  parametrize the closure-param shape in `required`. Use the closure
  body's invariant operation (`* 2`, `> 0.0`, etc.) as the required
  marker instead.

### Honest limitations (v4.1 candidates)

#### Library-group alts can't mix with inline alts in the same field

The harness's JSON parser substitutes `RUST_ALTERNATIVES_LIBRARY.NAME`
dotted references with the JSON of that group, but doesn't support JS
spread syntax (`{ ...LIB.GROUP, "extra": [...] }`). So a question that
wants BOTH library-group alts AND additional inline alts has to inline
the library group's contents — defeating the DRY benefit.

- No v4.0 question needs this combination; the limitation is a
  pedagogical-coverage issue, not a blocker. rs_int_06 needed multiple
  inline alts (closure-deref shape + sum-turbofish), and rs_int_05
  needed only the library group — no overlap.

- v4.1 candidate: extend the harness's reference-substitution to
  produce the merged-object JSON if the field uses spread syntax. Or,
  add a build-time pre-pass that resolves spreads into flat objects
  before the harness sees them.

#### Math-operator errors fall to "structure mismatch" fallback

Grammar-lite has tag-driven rules for mutability, closure-deref, missing
`;`, and missing `for <Type>` in impl blocks — but no rule for
arithmetic-intent mismatch. rs_int_06's first reject case (sum of
*doubles* instead of *squares*: `|&x| x + x` vs canonical `|&x| x * x`)
falls to fallback "structure mismatch."

- This is acceptable: the structure-mismatch diff still shows the
  user-provided line vs the canonical, so the operator difference is
  visible. The student can read it and self-correct.
- Encoding "math operator wrong" semantics in grammar-lite would
  require the grader to model arithmetic intent (sum-of-X vs
  product-of-X vs sum-of-something-else), which is outside the
  pattern-match scope.

- v4.1 candidate: not really — this is a documented boundary of
  pattern-match grading, not a fixable gap. If a track needs
  arithmetic-intent feedback (e.g., for numeric CUDA primitives),
  that's an argument for partial-execution support, not a
  grammar-lite extension.

### Closure-param corollary to the required-vs-alternatives boundary

The Amateur-tier rule has a third axis beyond token-prefix
(`Some` for `Some(_)`) and literal-suffix (`prediction.unwrap_or` for
`.unwrap_or(0.0)`): the *closure-parameter shape*.

- When a question accepts multiple closure-parameter patterns (e.g.
  `|x|`, `|&x|`, `|x| *x` for the same underlying variable `x`), the
  invariant across forms isn't a substring of all three — `|x|` is
  not a substring of `|&x|`. So requiring the bare-pattern form
  rejects the pattern-deref alternative.
- Fix: drop the closure-param shape from `required` entirely. Use the
  closure's **body operation** (`* 2`, `> 0.0`, `acc + x`) as the
  required invariant instead. The variable-name case (`|n|` vs `|x|`)
  falls to structure-mismatch with a diff, which is informative
  enough for the student to self-correct.

- Worked example: rs_int_04's first draft put `|x|` in required and
  the harness immediately rejected the `|&x| x * 2` accept variant
  ("missing `|x|`"). Removing `|x|` from required + keeping `* 2`
  resolved it.

- Rule: across the three identified boundaries (token-prefix,
  literal-suffix, closure-param), `required` holds the invariant that
  every accepted form *literally contains*. If no such invariant
  exists, drop the field; structure-match handles the rest.

### Operator-bracketed-by-invariants refinement (rs_int_07 acc + x)

rs_int_06 documented that bare math-operator errors fall to fallback
"structure mismatch" — grammar-lite has no arithmetic-intent rule, and
that's a documented boundary.

But rs_int_07 surfaced a useful refinement: when an operator sits
*between* invariant tokens — e.g. `acc + x` where both `acc` and `x`
are invariant across the accepted closure-deref variants — you can
require the operator-inclusive prefix `acc +`. A reject with the wrong
operator (`acc * x`) fails at the `required` step with a targeted
`missing `acc +`` message rather than falling to structure-mismatch.

- The same trick wouldn't work for rs_int_06's `x * x` because the
  closure-deref alts vary the surface around the operator — `|x|*x**x`
  doesn't contain `x*x` as a substring. The invariant-bracketing
  technique requires the operands themselves to be invariant.

- Rule: when an arithmetic operator sits between two invariant tokens,
  prefer to bracket it in `required` for targeted feedback on
  operator mistakes. When the operands are themselves parametric
  (closure-deref body, suffix variants), fall back to structure-
  mismatch with the diff.

### Deliberate-rhyme tradeoff: rs_int_05 ↔ rs_int_09

rs_int_05 (filter-count `weights > 0.0`) and rs_int_09 (filter-count
`scores > 0.5`) are structurally the same exercise — the rhyme is
intentional, reinforcing pattern-transfer (same iterator shape applies
across domain) and giving the closure-deref pattern two reps at this
tier.

- Conscious tradeoff: spends two of ten Intermediate slots on one
  iterator shape. Acceptable here because closure-deref is the
  MUST-include and rs_int_05 alone wouldn't give the student practice
  variation.
- If Master tier ends up thin on iterator-method variety (`.position`,
  `.any`, `.find`, `.fold` beyond what rs_int_07 already covers), the
  diversification belongs there, not by removing rs_int_09.

## Experienced tier

### ML-flavor lands at 50/10/40 — deliberate decision, not a calibration miss

Target for Experienced is 20/20/60. The tier cannot reach it, because
the 5 questions shipped in Stage 2 (rs_exp_01..05: trait def, impl,
generic identity, struct+lifetime, multi-T fn) are ALL pure Rust —
they were the "test both ends of complexity" representative slice,
authored before ML-flavor targets applied to authoring. Even if all 5
new questions were explicit ML, the ceiling is 50/0/50.

Decision (ruled 2026-05-19): land the full tier at **50/10/40**
(5 pure Stage 2 + 1 ML-adjacent + 4 explicit ML in the new 5).

- Precedent: v3.9's JS Experienced tier landed at 50/0/50 against the
  same 20/20/60 target, flagged as "classes-half pure-JS by necessity;
  ML half on target." Traits/generics/lifetimes in Rust are the
  structural analog of classes/inheritance in JS — inherently
  pure-language mechanics that resist ML framing.
- The slight improvement over JS (10 adjacent vs JS's 0) comes from
  two of the new concepts — multiple trait bounds (rs_exp_07) and
  `impl Iterator` (rs_exp_09) — admitting natural light ML framing
  (comparing scores; an epoch-step iterator) that JS classes/
  inheritance didn't.
- This is a DELIBERATE authoring decision constrained by the Stage 2
  representative slice, NOT a calibration miss. Surface it as such in
  the v4.0 CHANGELOG (Documented section), mirroring how v3.9
  documented its JS Experienced 50/0/50 landing.

### RESULT_PROPAGATION is mis-scoped (HEADLINE finding — rs_exp_10)

**This is the most significant authoring-discipline discovery of
Stage 3.** Unlike the required-vs-alternatives boundary hazard (a
mechanical grader-ordering issue the harness always catches), this is
a *semantic* miscalibration that the harness would have passed
silently while the question taught a falsehood.

The `RESULT_PROPAGATION` group declares `?` ≈ `.unwrap()` ≈
`.expect("error")` as interchangeable. They are NOT:

- `?` **propagates** — on `Err(e)` it returns the error from the
  enclosing function, letting the caller handle it.
- `.unwrap()` / `.expect()` **panic** — on `Err(e)` they abort the
  thread. This is the *opposite* failure behavior.

The group is correctly scoped ONLY for "extract the value" questions
where failure-handling is not the lesson (e.g. a lower-tier question
that just needs the f64 out of a known-good parse). It is WRONG for
any question whose lesson is propagation.

rs_exp_10's prompt is literally "propagate any error with the ?
operator." Accepting `.unwrap()` there would teach that `.unwrap()`
propagates — a falsehood. So rs_exp_10 uses NO alternatives, requires
`?` strictly, and adds a teaching-reject: a `.unwrap()` submission is
rejected with "missing `?`", actively correcting the exact
misconception the library group would have introduced.

- The group's NAME is misleading: it describes value-extraction, not
  propagation.
- v4.1 cleanup candidate: rename to `RESULT_VALUE_EXTRACTION` and
  document the scope boundary, OR split into a panic-forms group and
  a `?`-only group. For v4.0 the group stays as-is, unexercised.

### General principle: a library group's equivalence claim is tier-relative

A library `alternatives` group encodes a claim that its members are
equivalent. That claim is **tier-relative**. Forms that are
equivalent at a "get the value" tier (`.unwrap()` vs `?`) can be
semantically distinct at a "handle the failure" tier.

- Rule: before reusing a library group in a higher-tier question,
  verify the group's equivalence claim still holds for THAT question's
  specific lesson. Don't assume a group that fit at Amateur fits at
  Experienced/Master.
- rs_exp_10 is the worked example: the `?`/`.unwrap()` equivalence
  held at the Amateur "extract the value" framing (cf. rs_ama_08's
  `unwrap_or`, which is genuinely about defaulting, not propagation),
  but breaks at the Experienced "propagate the failure" framing.
- This is the semantic analog of the mechanical required-vs-
  alternatives boundary: both are "an alternatives entry can be wrong
  for a question," but the boundary hazard is caught by the harness
  (a correct answer fails) while the equivalence-scope error is NOT
  (a wrong answer passes). The harness guards the mechanical class;
  only author judgment guards the semantic class. This is the one
  place in v4.0 authoring where "run the harness" is not a sufficient
  safeguard.

### rs_exp_08 — boundary hazard caught pre-insertion (first time)

rs_exp_08 — required-vs-alternatives boundary hazard caught
pre-insertion (the `+=` in required vs the accepted alternative
`self.total = self.total + x` which contains no `+=` was spotted while
writing the draft, before any insertion or harness run).

**Correction (do not over-read the rs_exp_08 catch):** I initially
noted here that the rule was "internalized enough to fire during
authoring." That claim did NOT generalize. rs_exp_09, drafted in the
*same batch*, had the identical hazard in a different field — the
return-type alternative `-> Option<Self::Item>` vs `-> Option<usize>`
in required — and I missed it. The harness caught it (1 accept fail),
exactly as it caught rs_ama_06 and rs_int_04. Fix was the same:
replace the parametrized token in required with the invariant prefix
(`-> Option<`).

The honest read: this is the **fifth** appearance of the hazard
(rs_ama_06, rs_ama_08-design, rs_int_04, rs_exp_08, rs_exp_09). It is
the dominant authoring pitfall for this grader and it recurs across
EVERY field type that can carry an alternative — token suffix, closure
param, operator, assignment form, return type. The rs_exp_08
pre-insertion catch was luck of attention on one field, not a durable
skill that prevents the next one. The real safeguard is structural,
not cognitive: **the harness is the guard, run it every batch.** Any
field that has an `alternatives` entry must have its parametrized
token kept OUT of `required` — and the only reliable way to confirm
that across a multi-question batch is the harness, not author
vigilance.

- Rule (final form): for EVERY question, before running the harness,
  scan each `alternatives` key and confirm none of its variants would
  fail an entry in `required`. But do not trust that scan — the
  harness's per-accept-variant check is the actual guarantee. Treat a
  green harness as the gate, not a clean mental model.

### rs_exp_07 — strictness that teaches nothing gets an alternative

rs_exp_07's first draft locked the trait-bound order
(`<T: Copy + PartialOrd>` required as a full token), which would reject
the semantically-identical `<T: PartialOrd + Copy>`.

- Ruling (2026-05-19): ADD the reversed-order alternative, don't keep
  strict. The prior deliberate-strictness calls each taught a real
  distinction — rs_ama_02 (type-awareness), rs_ama_09 (idiomatic
  method choice). Rejecting reversed bound order teaches *nothing*:
  both orderings demonstrate identical understanding of multiple
  trait bounds, and rustfmt normalizes order anyway.
- When strictness teaches nothing, the "if an alternate demonstrates
  the same skill, accept it" principle wins over prompt-literalism.
- Implementation: `alternatives: { "<T: Copy + PartialOrd>": ["<T: PartialOrd + Copy>"] }`,
  the full bound-token dropped from `required` (boundary rule again —
  the order-bearing token can't be a required invariant if both
  orders are accepted), with `fn`/`larger`/`a: T`/`b: T`/`-> T`/
  `if a > b`/`else` as the order-free invariants and the bound
  presence verified by structure match.

- Distinction worth keeping straight: deliberate-strictness (reject)
  is right when the rejected form skips a *lesson*; accept-the-alternate
  is right when the rejected form demonstrates the *same* lesson by a
  different surface. The test is "does the rejected form show the
  student understood what this question teaches?" — if yes, accept it.
